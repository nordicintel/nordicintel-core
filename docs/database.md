# Database integration

## One definition of the schema

`src/nordicintel_core/database/schema.py` is the only place a table is declared. Alembic
revisions are generated from `Base.metadata`, repositories build their statements from the
same entities, and `tests/test_schema.py` fails if a migrated database and the declarative
model disagree. There are no packaged `.sql` resources: a schema edit that a query has not
followed is now a failing test rather than a runtime error.

`dataset` owns canonical/native identity, serving mode, operator controls, worker
availability, and `retired` (absence after authoritative discovery). `dataset_metadata`
owns the language-scoped combined metadata, including the publisher's nullable
`discontinued` flag. Retirement, publisher discontinuation, operator disabling and worker
availability are distinct states; `search` hides the first two by default and
`include_discontinued=True` shows both.

Every normalized metadata field is represented: scalar fields and text arrays are columns;
typed links, paths, contacts, PX details and extension maps use JSONB; dimensions and
categories are language-scoped child relations with `index` columns. Neither `id`/`size`
envelope arrays nor observations are stored. Comparison state, local harvest timestamps and
the GIN-backed search projection remain language-scoped. Model validation owns nested
semantic checks; SQL enforces keys, foreign keys, unique indexes, required scalar values,
enum values and JSON container types.

The Pydantic models in `nordicintel_core.models` remain the contract. They are not ORM
mappings, they import no SQLAlchemy, and no ORM instance leaves a repository: every method
returns a model.

## Engines and sessions

Applications create an engine, then pass a session to repositories. Which engine matters:

```python
from nordicintel_core.database import HarvestRepository, create_api_engine, session_scope

engine = create_api_engine(database_url)
with session_scope(engine) as session:
    jobs = HarvestRepository(session).list_jobs(limit=50)
```

A worker instead uses `create_owner_engine` and `owner_session`, which pin one physical
backend for the whole job:

```python
from nordicintel_core.database import create_owner_engine, owner_session

engine = create_owner_engine(harvest_database_url)
with owner_session(engine) as session:
    ...
```

Three rules keep that safe, and each has a test:

1. **One backend per job.** Ownership is enforced by `harvest_job.owner_backend_pid` and by
   session-scoped advisory locks. Both are silently lost if a pool hands out a different
   connection, so the owner engine uses `NullPool` and never pre-pings or recycles. If the
   connection is lost, stop — do not reconnect and resume protected writes.
2. **One transaction per call.** Every repository method is a single `session.begin()`
   block and leaves no transaction open, so a backend never sits idle in a transaction
   while a worker waits on an upstream request.
3. **Explicit columns on harvest writes.** Worker paths never load a `Dataset`, mutate it
   and flush; they issue updates that name only worker-owned columns, so a harvest cannot
   overwrite an operator's edit.

## Migrations

Run them exactly once as a separate deployment task, from the installed package:

```text
NORDICINTEL_DATABASE_URL=postgresql://... \
python -m nordicintel_core.database migrate upgrade
```

Supported commands are `upgrade [revision]`, `downgrade [revision]`, `current`, and
`check`. Upgrade defaults to `head`; downgrade defaults to `base`. API and worker startup
must not invoke them automatically.

`check` verifies both the applied revision *and* the shape of the database against
`Base.metadata`, so a database sitting at the right head with the wrong columns fails.

New revisions are autogenerated:

```text
alembic -c <config> revision --autogenerate -m "..."
```

Always review the result. Autogenerate does not reliably detect `CHECK` constraint changes
and will not render the regex checks at all, so a generated revision is a draft: diff it
against `schema.py`, and let `tests/test_schema.py` confirm the constraints and indexes
actually reach the database.

Deploy additive migrations before consumers that require them. Pin a tested core version in
every API, worker, and adapter lockfile; remove old schema fields only after all consumers
stop using them.
