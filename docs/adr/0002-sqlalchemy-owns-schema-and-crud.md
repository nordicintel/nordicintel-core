# SQLAlchemy owns the schema and ordinary CRUD

Supersedes [0001](0001-core-owns-postgres-schema.md), which kept the same ownership but
expressed it as hand-written SQL resources.

Core still owns one Alembic history and applications still never migrate on startup. What
changes is the source of truth: a SQLAlchemy declarative model in
`database/schema.py` defines every table, migrations are generated from it, and
repositories build statements from the same entities.

## Why

The no-ORM decision failed on its first schema change. `0001_initial.up.sql` was rewritten
against the combined Table/Dataset contract and the 55 packaged query files were not: they
still wrote `start_period`, `upstream_url`, `dimension.ordinal` and `dataset.discontinued`,
none of which existed any more. Nothing detected it, because nothing could — the SQL files
and the schema had no shared definition to disagree with. The mismatch was documented and
deferred rather than caught.

With one definition, that class of error is a failing test: `tests/test_schema.py` compares
a migrated database against `Base.metadata`, and the model-coverage assertion runs without
a database at all.

## What constrains it

The ORM is not allowed everywhere, because three properties of this system are easy to lose
to convenience and hard to notice when lost:

- **Ownership.** Advisory locks are session-scoped and `owner_backend_pid` is a physical
  backend id. Workers use a `NullPool` engine and hold one connection for the whole job.
- **Transaction scope.** Every repository method is one `session.begin()` block. Nothing
  may hold a transaction open across an upstream HTTP call.
- **Field ownership.** Harvest writes name their columns explicitly instead of flushing a
  loaded entity, so an operator's `operator_disabled` edit survives a concurrent harvest.

Accordingly the queue and metadata write paths use explicit Core constructs whose emitted
SQL and lock scope stay reviewable, while providers, schedules and job/item reads use
ordinary ORM queries.

## Consequences

- SQLAlchemy moves from a migration-only dependency into the `db` extra.
- Revisions are autogenerated but never trusted unreviewed: autogenerate cannot reliably
  diff `CHECK` constraints, so they are named and asserted against `pg_constraint`.
- `nordicintel_core.models` stays Pydantic-only and SQLAlchemy-free; ORM entities are an
  internal persistence detail that never crosses a repository boundary.
- Absence-based retirement (`dataset.retired`) and the publisher's `discontinued` flag are
  separate columns; both are hidden from search unless `include_discontinued` is set.
